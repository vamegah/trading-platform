# Production Operations Runbook

This runbook defines the minimum operational procedures required before live trading is enabled.

## Incident Severity

| Severity | Trigger | Response Target | Examples |
| --- | --- | --- | --- |
| SEV-1 | Customer capital, live execution, data integrity, or platform availability is materially at risk | Immediate page, commander assigned within 5 minutes | Erroneous orders, broker outage during live trading, corrupted market data, auth bypass |
| SEV-2 | Major feature or market-hours workflow degraded with workaround available | Triage within 15 minutes | Scanner latency breach, delayed alerts, single provider outage with failover active |
| SEV-3 | Non-critical degradation outside market-critical path | Triage next business day | Dashboard cosmetic issues, delayed non-trading reports |

## Black-Swan or Manual Trading Pause

1. Open the safety admin control or call the safety service pause endpoint.
2. Set platform mode to `manual_pause`.
3. Confirm new orders are rejected by execution preflight checks.
4. Cancel eligible pending orders when market conditions make execution unsafe.
5. Notify customers if live or automated trading was affected.
6. Record the event in the audit log with the operator, reason, affected strategies, and restart criteria.
7. Resume only after risk, compliance, and operations approve the restart.

## Broker Outage

1. Confirm outage through broker status page, API health check, and failed reconciliation jobs.
2. Disable affected broker routing in execution configuration.
3. Route eligible orders to approved alternate brokers only if suitability, permissions, and account capability checks pass.
4. Reconcile open orders, positions, balances, and fills when connectivity returns.
5. Compare broker fills against internal trade journal and repair mismatches through an audited adjustment.

## Market Data or Alternative Data Outage

1. Identify stale, missing, or outlier data source through data quality reports.
2. Fail over to secondary providers when confidence and latency thresholds are met.
3. Mark affected signals as degraded or stale when failover cannot meet policy.
4. Block new recommendations that depend on unavailable critical data.
5. Backfill raw and feature stores after the outage and record new dataset versions.

## Data Corruption

1. Freeze affected datasets and prevent downstream feature publication.
2. Identify last known-good data lake version and snapshot hash.
3. Restore from immutable backup or regenerate from raw provider payloads.
4. Re-run data quality, look-ahead, corporate action, and point-in-time checks.
5. Recompute any recommendations created from corrupted snapshots and disclose impact if user-facing decisions changed.

## Model Rollback

1. Demote the active champion model in the model registry.
2. Promote the previous approved champion version.
3. Clear cached signals generated by the failed model.
4. Re-run calibration, drift, explainability, and challenger comparison checks.
5. Audit the rollback with model version IDs, affected signals, and reason codes.

## Secret or Key Rotation

1. Generate replacement keys in the approved secret manager or KMS.
2. Store the new secret version and mark previous versions inactive.
3. Restart or refresh services that consume the secret.
4. Verify no plaintext secret appears in logs, metrics, traces, or audit payloads.
5. Revoke the old key after successful validation and record the rotation in the audit trail.

## Disaster Recovery

1. Declare DR mode and identify primary-region failure scope.
2. Restore database, object storage, audit metadata, and data lake manifests in the secondary region.
3. Verify RTO/RPO results against the active SLO.
4. Run smoke tests for auth, signals, portfolio risk, paper trading, and broker connectivity.
5. Keep live trading disabled until data reconciliation and compliance approval are complete.

## Customer Communications

1. Publish initial notice for SEV-1 customer-impacting events within the approved communication window.
2. Include affected services, current trading restrictions, customer action required, and next update time.
3. Do not include speculative root cause or regulated advice.
4. Publish post-incident review after remediation and compliance approval.
